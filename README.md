# Умный дом

Многопользовательская платформа управления домашними устройствами на базе
ESP8266, шестиканального релейного модуля и датчика DHT22.

Один backend и один веб-интерфейс обслуживают любое число пользователей.
Каждый после входа получает своё состояние: свои устройства, настройки,
автоматизации, сценарии и свой состав главного экрана. Данные одного
пользователя другому недоступны — подстановка чужого идентификатора в запрос не
даёт ничего, потому что владельца берут из сессии, а не из тела запроса.

Управление идёт через веб-интерфейс и бот Telegram, понимает команды на русском
языке, ведёт климат автоматически и умеет откладывать задачи на будущее.

## Состав

| Часть | Что это |
| ----- | ------- |
| `src/backend` | Вся логика на Python: FastAPI, SQLAlchemy, понимание фраз |
| `src/frontend` | Веб-интерфейс на React: карточки устройств, климат, чат |
| `src/firmware` | Прошивка ESP8266: реле, датчик, дозвон до сервера |
| `build/alembic` | Ревизии схемы базы |
| `docs` | Архитектура, протокол платы, железо, API |

## Как это работает

```
браузер / WebSocket / Telegram
        ↓ Bearer-токен
     Backend          ← сессии, логика, база, понимание фраз, планировщик
        ↑ WebSocket    (плата дозванивается сама, по ключу сопряжения)
     ESP8266          ← только реле и датчик
        ↓
   DHT22 / реле ×6
```

Главный принцип: **одно приложение → много пользователей → индивидуальное
состояние каждого**. Хранится состояние, а не копия интерфейса. Сервисов тут два:
веб-процесс (`python -m backend.main`) отвечает на запросы и держит сокеты плат, а
рабочий (`python -m backend.worker_entry`) ведёт фоновые циклы — климат, сценарии и
очистку объявлений плат, которые никто не забрал. У обоих одна конфигурация и одна
база, поэтому рабочих можно запускать несколько: перед каждым периодом аккаунт
берёт в Redis аренду, и обслуживает его ровно один инстанс. Frontend —
универсальный рендерер: сервер отдаёт список виджетов (`тип`, `устройство`,
`заголовок`), и компоненты `TemperatureCard`, `DeviceCard`, `ClimateCard`,
`CommandChat` для всех одни и те же. Различаются данные, порядок и личные
заголовки.

Плата ничего не решает: она исполняет команды и сообщает о состоянии. Выбор
устройства, климатическая автоматизация, сценарии и разбор фраз живут в backend.
Логические устройства отделены от физических каналов, поэтому «Relay 3» можно
переназначить с кондиционера на увлажнитель, не перепрошивая плату.

## Возможности

- Шесть релейных каналов с настраиваемыми названиями и типами
- Климат по DHT22 с гистерезисом, чтобы устройства не метались вокруг цели
- Автоматика, ищущая устройство по capability, а не по имени или каналу
- Сценарии с отложенным стартом и тремя вариантами завершения
- Команды на русском: «включи свет», «тут жарко», «через полчаса сделай 20 градусов»
- Уведомления в Telegram о значимых событиях и команды тем же текстом
- Приоритеты: авария → сценарий → автоматика → ручное управление с окном
- Realtime-обновления интерфейса через WebSocket, без перезагрузки
- Регистрация и вход, изоляция данных между аккаунтами
- Персональный главный экран: состав, порядок карточек и их названия
- Сопряжение плат по ключу: плата дозванивается до удалённого сервера сама
- Несколько плат на один аккаунт: реестр соединений ключуется «аккаунт + плата»
- Настройка сети платы без прошивки: своя точка доступа или команда сервера

## Запуск

### Backend

```bash
python -m venv .venv
.venv/bin/pip install -e ".[dev]"
cp .env.example .env                  # и задать AUTH_TOKEN_SECRET
PYTHONPATH=src python -m backend.main
```

Интерфейс откроется на <http://127.0.0.1:8000>, описание API — на `/docs`.
Первый пользователь регистрируется через `/api/auth/register` и сразу получает
свой набор устройств, настроек и главный экран.

Схема на PostgreSQL и ведётся ревизиями из `build/alembic`:

```bash
PYTHONPATH=src .venv/bin/alembic -c build/alembic/alembic.ini upgrade head
```

Фразы человек читает русские, поэтому `AUTH_TOKEN_SECRET` задают обязательно:
без него процесс не стартует, а выдуманный на лету секрет выкидывал бы всех из
сессии при каждом перезапуске.

Через Docker (собирает интерфейс и кладёт его рядом с пакетом, поэтому весь
продукт работает из одного образа и одного origin):

```bash
AUTH_TOKEN_SECRET=$(openssl rand -hex 32) docker compose up --build
```

### Frontend

Для разработки:

```bash
cd src/frontend
npm install
npm run dev
```

Сборка в production — результат кладётся в `src/frontend/dist` и раздаётся
backend'ом автоматически:

```bash
npm run build
```

### Прошивка

Настройки сети **не зашиты в код**. Плата, которой ещё не задали сеть, поднимает
точку доступа `SmartHome-Setup-XXXXXX` и отдаёт с неё страницу:

1. Подключитесь к этой точке (пароля нет) и откройте `http://192.168.4.1/`.
2. Введите имя домашней сети, её пароль и адрес сервера.
3. Нажмите «Сохранить и подключиться».

Плата записывает значения в свою память, отключает точку доступа и входит в
сеть. Дальше откройте панель сервера и заберите плату себе. Позже сеть меняется
в панели: «Платы» → «Сеть» → «Применить»; backend отправляет плате новые значения
по тому же сокету, и та переподключается сама. Плата, потерявшая сеть, поднимает
точку доступа снова.

```bash
cd src/firmware
pio run -t upload
pio device monitor
```

Веб-интерфейс прошивка не раздаёт и чужие HTTP-запросы не проксирует: интерфейс
отдаёт backend, а плата остаётся чистым драйвером. Кадры JSON строятся и читаются
ArduinoJson — документом на стеке, без аллокаций в куче и с корректным
экранированием имени сети и пароля. Флеш-память перезаписывается только когда
значение действительно изменилось. Пины: `D1`-`D6` — шесть
каналов реле, `D7` — DATA датчика DHT22, реле активны низким уровнем.
Подробности и предупреждение про бутстрап-пины —
в [docs/hardware/pinout.md](docs/hardware/pinout.md).

## Настройка

Все параметры читаются из окружения, полный список — в `.env.example`. Значения
не раскиданы по коду: у каждой секции свой файл в `src/backend/config/sections`,
а плоский `Settings` собирает их вместе (Pydantic для конфигурации не используется).

| Переменная | Назначение |
| ---------- | ---------- |
| `DATABASE_URL` | Подключение к PostgreSQL |
| `REDIS_URL` | Живое состояние, события и аренды |
| `AUTH_TOKEN_SECRET` | Секрет подписи сессионных токенов |
| `AUTH_SESSION_LIFETIME_MINUTES` | Сколько живёт токен |
| `BOARD_SOCKET_PORT` / `BOARD_SOCKET_PATH` | Куда дозваниваются платы |
| `BOARD_COMMAND_TIMEOUT_SEC` | Сколько команда ждёт подтверждения |
| `TELEGRAM_ENABLED` / `TELEGRAM_BOT_TOKEN` | Поднимать ли бота и каким ключом |
| `LANGUAGE_MODEL_NAME` / `LANGUAGE_CONFIDENCE_THRESHOLD` | Кодировщик фраз и порог уверенности |
| `AUTOMATION_CYCLE_SEC` / `AUTOMATION_SCENARIO_TICK_SEC` | Периоды фоновых циклов |

## Разработка

```bash
.venv/bin/ruff check src tests scripts      # стиль
.venv/bin/ruff format src tests scripts     # формат
.venv/bin/lint-imports                      # границы слоёв
.venv/bin/pytest                            # тесты
PYTHONPATH=src .venv/bin/python scripts/check_app_wires.py
```

Последняя команда собирает контейнер зависимостей и разрешает **каждый** его узел
(прикладные сервисы, сценарии, точки входа запроса) и печатает опубликованные
маршруты: контейнер строится лениво, и провайдер с неподходящей сигнатурой
всплывает только когда ключ впервые попросили.

Архитектурные границы проверяются `import-linter`: domain не зависит ни от FastAPI,
ни от SQLAlchemy, ни от Telegram, а прикладной слой не заглядывает в
инфраструктуру.

## Команды

Понимаются свободные формулировки:

```
включи свет
зажги лампу
выключи всё
тут жарко
сделай прохладнее
сделай влажность 45 процентов
какая температура?
через полчаса сделай 20 градусов
отмени сценарий
```

## Telegram

Бот работает от имени конкретного аккаунта. Пароль в чат не пишется: интерфейс
выдаёт одноразовый код привязки, а боту его пересылают сообщением

```
link:<код>
```

Дальше все команды этого чата исполняются в доме привязанного аккаунта, а
уведомления о значимых событиях приходят в тот же чат. Распознавания голоса в
системе нет: бот понимает текст.

## Ограничения

* Пароли хешируются PBKDF2-HMAC-SHA256 (`hashlib`, без внешней зависимости);
  хранимая форма начинается с имени алгоритма, поэтому переход на bcrypt или
  argon2 — шаг кода, а не перенос данных.
* Токены сессии не хранятся на сервере: потеря ключа подписи разлогинивает всех.
* Понимание фраз опирается на локальный кодировщик предложений; без модели
  команда остаётся нераспознанной, и система переспрашивает.
* Автоматика и сценарии обслуживаются последовательно по аккаунтам; два воркера
  не берут один дом благодаря аренде в Redis.
