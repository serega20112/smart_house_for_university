# Умный дом

Многопользовательская платформа управления домашними устройствами на базе
ESP8266, шестиканального релейного модуля и датчика DHT22.

Один backend и один веб-интерфейс обслуживают любого числа пользователей.
Каждый после авторизации получает своё состояние: свои устройства, настройки,
автоматизации, сценарии и свой состав главного экрана. Данные одного
пользователя недоступны другому — подстановка чужого идентификатора в запрос
не даёт ничего.

Управление идёт через веб-интерфейс и Telegram, понимает команды на русском
языке, ведёт климат автоматически и умеет откладывать задачи на будущее.

## Состав

| Часть | Что это |
| ----- | ------- |
| `firmware` | Прошивка ESP8266: реле, датчик, обмен с backend |
| `backend` | Вся бизнес-логика на Python: FastAPI, SQLAlchemy, NLP |
| `frontend` | Веб-интерфейс на React: карточки устройств, климат, чат |
| `docs` | Схемы, протокол обмена, описание железа |

## Как это работает

```
браузер / Telegram
        ↓ Bearer-токен
     Backend          ← сессии, вся логика, база, понимание команд
        ↑ WebSocket    (плата дозванивается сама, по ключу сопряжения)
     ESP8266          ← только реле и датчик
        ↓
   DHT22 / Реле ×6
```

Главный принцип: **один шаблон приложения → множество пользователей →
индивидуальное состояние каждого пользователя**. Хранится состояние, а не
отдельная копия интерфейса. Frontend — универсальный рендерер: сервер отдаёт
список виджетов (`тип`, `устройство`, `заголовок`), а компоненты
`TemperatureCard`, `DeviceCard`, `ClimateCard`, `CommandChat` одни и те же для
всех аккаунтов. Различаются только данные, порядок и личные заголовки.

ESP8266 ничего не решает: он исполняет команды и сообщает о состоянии.
Выбор устройства, климатическая автоматизация, сценарии и разбор команд
выполняются в backend.

Логические устройства отделены от физических каналов, поэтому «Relay 3»
можно переназначить с кондиционера на увлажнитель, не перепрошивая плату.

## Возможности

- Шесть релейных каналов с настраиваемыми названиями и типами
- Климат по DHT22 с гистерезисом, чтобы устройства не метались
- Автоматический режим с выбором устройства по capability, а не по каналу
- Сценарии с отложенным стартом и тремя вариантами завершения
- Команды на русском: «включи свет», «тут жарко», «через полчаса сделай 20 градусов»
- Уведомления в Telegram о значимых событиях
- Приоритеты: авария → сценарий → автоматика → ручное управление
- Realtime-обновления интерфейса через WebSocket, без перезагрузки
- Регистрация и вход, изоляция данных между пользователями
- Персональный главный экран: состав, порядок карточек и их названия
- Сопряжение плат по ключу: ESP подключается к удалённому серверу сам
- Настройка сети платы без прошивки: своя точка доступа или команда от сервера

## Запуск

### Backend

```bash
cd backend
pip install -e ".[dev]"
python -m smart_home_backend.main
```

Интерфейс откроется на <http://127.0.0.1:8000>, документация API — на `/docs`.
Первый пользователь регистрируется через `/register` и сразу получает свой
набор устройств, настроек и главный экран.

Схема базы стала user-scoped, поэтому базу, созданную версией до
многопользовательской, нужно удалить: `rm backend/src/smart_home_backend/smart_home.db`
(в контейнере — том `backend-data`).

Задайте `AUTH_TOKEN_SECRET` в окружении, иначе секрет подписи генерируется
при каждом старте и сессии не переживают перезапуск.

Через Docker (собирает интерфейс и кладёт его рядом с пакетом, поэтому весь
продукт работает из одного образа и одного origin):

```bash
AUTH_TOKEN_SECRET=$(openssl rand -hex 32) docker compose up --build
```

### Frontend

Для разработки:

```bash
cd frontend
npm install
npm run dev
```

Сборка в production — результат кладётся в `frontend/dist` и раздаётся
backend'ом автоматически:

```bash
npm run build
```

### Прошивка

Настройки сети **не зашиты в код**. Плата, которой ещё не задали сеть,
поднимает точку доступа `SmartHome-Setup-XXXXXX` и отдаёт с неё страницу:

1. Подключитесь к этой точке (пароля нет) и откройте `http://192.168.4.1/`.
2. Введите имя домашней сети, её пароль и адрес сервера.
3. Нажмите «Сохранить и подключиться».

Плата записывает значения в свою память, отключает точку доступа и
подключается к сети. Дальше откройте панель сервера и заберите плату себе.

Сменить сеть позже можно в панели: «Платы» → «Сеть плат» → «Применить». Backend
отправляет плате новые значения по тому же сокету, и та переподключается сама.
Плата, потерявшая сеть, поднимает точку доступа снова — данные можно вписать
заново.

```bash
cd firmware/src
pio run -t upload
```

Список портов: `D1`-`D6` — реле, `D7` — data DHT22. Реле активны по низкому
уровню.

## Настройка

Все параметры читаются из окружения, полный список — в `backend/.env.example`.

| Переменная | Назначение |
| ---------- | ---------- |
| `DATABASE_URL` | Подключение к базе, по умолчанию SQLite |
| `AUTH_TOKEN_SECRET` | Секрет подписи сессионных токенов |
| `AUTH_SESSION_LIFETIME_MINUTES` | Сколько живёт токен, по умолчанию 30 дней |
| `ESP_SERVER_HOST` / `ESP_SERVER_PORT` | Куда подключается ESP8266 |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | Бот и разрешённый чат |
| `NLP_CONFIDENCE_THRESHOLD` | Порог, ниже которого система переспрашивает |
| `NLP_ALLOW_LEXICAL_FALLBACK` | Разрешить лексический эмбеддер без модели |

## Разработка

```bash
cd backend
pytest                          # тесты
lint-imports                    # границы слоёв
ruff check src                  # стиль
```

```bash
cd frontend
npm run typecheck               # типы интерфейса
```

Архитектурные границы проверяются автоматически: domain не зависит ни от
FastAPI, ни от SQLAlchemy, ни от Telegram. Изоляция данных закреплена тестами
`backend/tests/integration/test_api.py` и `test_database.py`: там проверяется,
что чужое устройство читается как отсутствующее, а команда к нему не доходит
до платы.

## Команды

Понимаются свободные формулировки:

```
включи свет
зажги лампу
выключи всё
тут жарко
сделай прохладнее
сделай влажность 45 процентов
какая температура?
через полчаса сделай 20 градусов
отмени сценарий
```

## Telegram

Бот работает от имени конкретного аккаунта. Привязка чата выполняется один раз:

```
/login vasya@example.com super-secret-1
```

Все команды из этого чата исполняются в рамках этого пользователя.

## Ограничения MVP

* Пароли хешируются PBKDF2-SHA256, токены — HMAC без хранения на сервере.
* Один пользователь — одна плата: живое состояние ведётся по `UserId`, поэтому
  несколько плат на один аккаунт потребуют расширения реестра состояния.
* Автоматизация и сценарии планировщик обслуживает последовательно по всем
  аккаунтам, а не параллельно.
