# REST API бэкенда

Базовый адрес: `http://<host>:8000`. Все ответы — JSON. События в реальном времени —
WebSocket `ws://<host>:8000/ws` (см. ниже). Публичная спека живёт в `/docs` самого
приложения: эта страница описывает то же контракт, но словами.

## Авторизация

Единственный способ узнать, кто делает запрос, — сессионный токен. Он подставляется в
заголовок `Authorization: Bearer <token>`. Идентификатор пользователя, присланный
клиентом в теле или в query, не читается никогда: бэкенд определяет аккаунт только из
токена.

Публичных ручек ровно четыре: регистрация, вход, выход и проверка доступности сервиса.
Все остальные возвращают `401`, если токена нет или он недействителен.

| Метод | Путь | Описание |
| --- | --- | --- |
| POST | `/api/auth/register` | `{email, password, display_name}` → `201` с сессией (токен + профиль) |
| POST | `/api/auth/login` | `{email, password}` → сессия |
| POST | `/api/auth/logout` | `{status, message}`: клиенту где забыть токен |
| GET | `/api/auth/me` | Профиль текущего аккаунта |
| POST | `/api/auth/realtime-ticket` | `{ticket, expires_in_sec}`: одноразовый билет для WebSocket |
| GET | `/api/health` | `{status, name, version}`, доступно без токена |

Сессия — подпись HS256 с ограниченным сроком: её не хранят, поэтому выход ничего не
удаляет на сервере. Ошибки: `409` — логин уже занят, `422` — некорректный логин, имя
или слишком короткий пароль (минимум 8 знаков), `401` — неверные учётные данные.

## Состояние дома и персональная проекция

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/state` | Полный снимок аккаунта: `board_online`, `automation_suspended`, `reading`, `devices`, `automation`, `active_scenarios` |
| GET | `/api/preferences` | Настройки интерфейса: `temperature_unit`, `theme`, `language`, `show_command_chat` |
| PATCH | `/api/preferences` | Частичное изменение тех же полей |
| GET | `/api/dashboard` | Состав главного экрана: `{widgets: [{type, device_id, title}]}` |
| PATCH | `/api/dashboard` | Замена раскладки целиком: `{widgets: [...]}` |

Тип виджета — один из `climate`, `sensor`, `device`, `command`. Экран не знает этих
имён заранее: он выбирает по типу готовый компонент и передаёт ему личный `title`.
Виджет, указывающий на чужое устройство, отклоняется с `422` — правило владельца живёт
в агрегате раскладки, а не в проверке запроса.

`/api/state` собирается одним сценарием приложения, поэтому числа на экране принадлежат
достаточно близким моментам, чтобы им можно было верить.

## Устройства

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/devices` | Список устройств аккаунта с их живым состоянием |
| POST | `/api/devices` | Создать устройство `{name, kind, channel, capabilities[], enabled, automation_enabled}` → `201` |
| PATCH | `/api/devices/{id}` | Частичное изменение тех же полей |
| DELETE | `/api/devices/{id}` | Удалить устройство → `204` |
| POST | `/api/devices/{id}/capabilities/{capability}` | Попросить устройство выполнить способность |

Способность — одно из `ON`, `OFF`, `COOL`, `HEAT`, `HUMIDIFY`, `DEHUMIDIFY`; переключать
можно только то, что устройство умеет. Назначение (`kind`) — одно из `LIGHT`, `FAN`,
`HUMIDIFIER`, `DEHUMIDIFIER`, `AIR_CONDITIONER`, `HEATER`, `OUTLET`, `OTHER`.

Ответ на переключение — устройство в том состоянии, которого оно достигло: экран не
угадывает его сам. Состояние принимает `OFF`, `ACTIVE`, `COOLING`, `HEATING`,
`HUMIDIFYING`, `DEHUMIDIFYING`, `UNAVAILABLE`.

Ошибки: `409` — канал уже занят другим устройством **этого же аккаунта**, `502` — плата
не подтвердила команду, `404` — устройства нет, `422` — способность не поддерживается
или канал вне 1..32.

Устройство чужого аккаунта читается как отсутствующее: подстановка чужого `id` даёт
`404`, а не его данные. Канал реле уникален внутри аккаунта, поэтому два пользователя
спокойно занимают один и тот же канал на своих платах.

## Платы (ESP8266)

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/esp-devices` | Платы аккаунта с признаком `online` |
| POST | `/api/esp-devices` | Сопряжение `{name, pairing_key?}` → `201`; ключ отдаётся ровно один раз |
| GET | `/api/esp-devices/claims` | Платы, которые ищут хозяина |
| POST | `/api/esp-devices/claims` | Забрать объявленную плату `{claim_token, name}` → `201` |
| DELETE | `/api/esp-devices/{id}` | Отвязать плату → `204` |
| GET | `/api/esp-devices/{id}/network` | Сеть, предписанную плате |
| PUT | `/api/esp-devices/{id}/network` | Задать сеть `{ssid, password, host, server_port, socket_port, socket_path}` |

Сопряжённая вручную плата отдаёт `pairing_key` — именно его она предъявляет при дозвоне.
Второй способ не требует ключа вовсе: плата, у которой нет хозяина, объявляет себя сама,
а `GET /api/esp-devices/claims` показывает её код и токен предложения.

Настройки сети меняются на лету: бэкенд отправляет плате `SET_NETWORK`, она пишет их в
свою память и переподключается. Значения сохраняются и тогда, когда плата сейчас не на
связи, — она получит их при следующем подключении. Пароль сети в ответе не приходит
никогда.

## Автоматизация

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/automation` | Настройка: `enabled`, `target_temperature`, `target_humidity`, `temperature_tolerance`, `humidity_tolerance`, `participating_device_ids` |
| PUT | `/api/automation` | Частичное изменение той же настройки |

Хранились бы `min/max` температуры, экран спорил бы с сервером о том, какой гистерезис
действует: цель и допуск — одно решение, и оно приходит одним числом на каждую
величину. Пустой `participating_device_ids` значит «каждое согласившееся устройство».
Режим AUTO включается тем же `PUT` (`{enabled: true}`): отдельных ручек включения и
выключения нет.

## Сценарии

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/scenarios` | Все сценарии аккаунта |
| POST | `/api/scenarios` | Поставить `{capability, delay_minutes, target_temperature, target, completion_behavior, duration_minutes}` → `201` |
| DELETE | `/api/scenarios/{id}` | Отменить сценарий, вернув его тело |

`completion_behavior` — один из `LEAVE_TO_AUTOMATION`, `SWITCH_EVERYTHING_OFF`,
`RESTORE_CAPTURED_STATE`. Сценарий ставится и снимается также свободной командой;
отдельной ручки «запустить вручную» нет, потому что цикл автоматики запускает фоновый
процесс.

## Команды

| Метод | Путь | Описание |
| --- | --- | --- |
| POST | `/api/commands` | `{text}` — предложение своими словами |

Ответ: `{intent, answer, message, details}`, где `answer` — фраза, которую видят
человеку. Команда исполняется в рамках аккаунта сессии: она видит только его устройства
и меняет только их состояние. Если предложение нельзя выполнить как оно есть, приходит
`422` с причиной — по ней интерфейс и задаёт встречный вопрос.

## Realtime

Интерфейс открывает поток событий по одноразовому билету, а не по токену сессии.
Сначала `POST /api/auth/realtime-ticket` (с `Authorization: Bearer <access_token>`) выдаёт
`{ticket, expires_in_sec}` — короткоживущий билет (по умолчанию 30 секунд). Затем
WebSocket `ws://<host>:8000/ws?ticket=<ticket>`: сервер меняет билет на аккаунт ровно
один раз и закрывает соединение до приёма, если билет истёк, неизвестен или уже погашен.
Токен сессии в строке запроса не появляется, поэтому утёкший адрес (в логах прокси,
истории браузера, Referer) доступа к дому не даёт.

Подписка привязана к аккаунту: соединение получает только события своего владельца.
Имена событий заданы одним перечислением (`domain/events.py`):

| Событие | Данные |
| --- | --- |
| `board.online`, `board.offline` | `{board_id}` |
| `board.error` | `{board_id, code, message}` |
| `board.relay_changed` | `{board_id, device_id, name, channel, status}` |
| `board.paired` | `{board_id, name}` |
| `board.announcement_published` | `{label, claim_token, expires_at}` (broadcast) |
| `device.state_changed` | `{device_id, name, channel, status}` |
| `devices.updated` | одно из `created`, `updated`, `deleted` — идентификатор устройства, плюс `name` при создании |
| `automation.updated` | `{updated: true}` |
| `scenario.scheduled`, `scenario.started`, `scenario.finished` | снимок сценария |
| `sensor.temperature_changed` | `{temperature}` |
| `sensor.humidity_changed` | `{humidity}` |

Экран применяет событие на месте там, где изменение выразимо заплаткой (показания
климата, состояние одного устройства), и перечитывает снимок целиком там, где нет
(список устройств, очередь сценариев, доступность платы).
