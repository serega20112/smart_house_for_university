# Архитектура системы

## Три уровня ответственности (ТЗ п.42)

```text
ESP8266        -> физическое исполнение (реле, датчик) и трансляция показаний
Backend        -> ВСЯ бизнес-логика: устройства, автоматизация, сценарии, NLP
Frontend / TG  -> только интерфейс пользователя
```

* ESP8266 не принимает решений за систему.
* Frontend и Telegram не управляют ESP напрямую.
* Backend — единственная точка, через которую проходят команды и автоматизация.
* Clean Architecture применяется **только к backend**.

## Многопользовательская схема

Один backend, один frontend, одна схема приложения — и персональная проекция
этого приложения для каждого аккаунта:

```text
                    ┌─────────────────────┐
                    │      Backend        │
                    │                     │
                    │ Auth   Users        │
                    │ Devices UserState   │
                    │ API    Database     │
                    └──────────┬──────────┘
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
              User A                       User B
                 │                           │
       ┌─────────┴─────────┐     ┌───────────┴─────────┐
       │                   │     │                     │
    Devices             State  Devices               State
    Preferences     Dashboard  Preferences         Dashboard
    Automation      Scenarios   Automation          Scenarios
```

Пользователь получает не копию приложения, а собственную проекцию: хранятся
данные состояния, а не отдельная сборка или отдельная страница.

### Как обеспечивается изоляция

1. **Идентификатор.** Аккаунт получает `UserId` — UUID (`UserId.generate()`).
   Он связывает сущности между собой, но не является пропуском: авторизация идёт
   через токен.
2. **user-scoped хранение.** `devices`, `automation`, `scenarios`,
   `user_preferences`, `dashboards`, `esp_devices` несут `user_id`.
3. **Owner в сигнатуре.** `DeviceRepository.list_all(user_id)`,
   `get(user_id, device_id)`, `delete(user_id, device_id)` и так далее: идентификатор
   владельца передаётся явно, поэтому изоляция видна в коде, который делает
   запрос, а не спрятана в транзакции.
4. **Аккаунт из токена.** `CurrentUserId` — зависимость FastAPI, которая
   достаёт `UserId` из bearer-токена. Ни один route не читает `user_id` из тела
   или query.
5. **User-scoped runtime.** `HomeRuntimes` отдаёт каждому аккаунту свой
   `HomeRuntime` с собственными реле, показаниями датчиков и окном ручного
   управления.
6. **User-scoped события.** `EventBus.publish(user_id, ...)` раздаёт событие
   только сокетам этого аккаунта.
7. **User-scoped платы.** `EspConnection` держит сессии в `dict[UserId, ...]`,
   а `EspGateway.set_relay(user_id, ...)` адресует конкретную плату.

Подстановка чужого UUID в запрос не даёт ничего: чужое устройство читается как
отсутствующее (`404`), а команда к нему не доходит до платы.

## Общая схема

```text
                    ┌─────────────────┐
                    │    Frontend     │
                    └────────┬────────┘
                             │ REST + WebSocket
                             ▼
                    ┌─────────────────┐
                    │     Backend     │
                    │ Clean           │
                    │ Architecture    │
                    └────────┬────────┘
                             │
                 ┌───────────┴───────────┐
                 │                       │
                 ▼                       ▼
          ┌─────────────┐         ┌─────────────┐
          │  Telegram   │         │    ESP8266  │
          └─────────────┘         └──────┬──────┘
                                         │
                              ┌──────────┴──────────┐
                              │                     │
                           DHT22                Relay ×6
```

ESP8266 устанавливает **исходящее** WebSocket-соединение к backend
(`ws://<backend>:8765/esp`), поэтому ESP не обязан иметь стабличный IP и
не принимает входящих соединений. Backend держит сервер `websockets` на порту 8765.

## Слои backend

```text
Presentation  (FastAPI REST, WebSocket для frontend, Telegram-хендлеры)
     ↓
Application   (commands/queries — use cases, движки автоматизации и сценариев)
     ↓
Domain        (сущности, value objects, enums, интерфейсы репозиториев, доменные сервисы)
     ↑
Infrastructure (SQLAlchemy, ESP-клиент, Telegram API, embeddings/NLP)
```

Зависимости направлены внутрь. Domain не знает про FastAPI, SQLAlchemy,
Telegram, ESP и конкретную библиотеку embeddings — он зависит только от
абстрактных интерфейсов (`repositories/`, порты в application).

## Ключевые решения

| Решение | Обоснование |
| --- | --- |
| Логические устройства ≠ физические реле | Пользователь переименовывает/переназначает каналы без прошивки (ТЗ п.10) |
| capabilities (ON/OFF/COOL/HEAT) | Автоматизация ищет устройство по возможности, а не по имени (ТЗ п.11) |
| Единый разбор команды | Web и Telegram сходятся в один pipeline обработки текста (ТЗ п.12, 38) |
| Hysteresis-диапазон | Защита от дребезга включения около цели (ТЗ п.21) |
| Приоритеты: аварийные > сценарий > автоматика > ручное | Детерминированное поведение при конфликтах (ТЗ п.25) |
| MANUAL_OVERRIDE с таймером | Ручная команда временно глушит автоматику |
| Embeddings + fallback-скорер | Понимание формулировок без LLM; при недоступности модели — лексический fallback (ТЗ п.15–17) |
| Аккаунт — первый аргумент use case | Изоляция видна в сигнатуре, а не в договорённости (ТЗ п.4, 11) |
| Живое состояние не в репозитории | `HomeRuntimes` держит горячее состояние в памяти и создаёт его по `UserId` |
| Статeless-токены (HMAC) | Нет хранилища сессий; смена секрета разлогинивает всех, что верно для свежего деплоя |
| Дашборд — данные, а не разметка | `widgets: [{type, device_id, title}]`; фронтенд остаётся универсальным рендерером (ТЗ п.6, 12) |
| Плата дозванивается сама | Исходящее соединение ESP к удалённому backend по ключу сопряжения (ТЗ п.9) |

## NLP-pipeline (ТЗ п.15)

```text
Нормализация → Embedding → Векторный поиск → Intent → Парсер параметров
→ StructuredCommand → Application
```

При уверенности ниже `NLP_CONFIDENCE_THRESHOLD` команда не выполняется —
система просит уточнение (ТЗ п.17, критерий 15).

## Потоки событий

1. ESP присылает `STATE`/`SENSOR_DATA` → `EspClient` обновляет `HomeState` →
   `EventBus` рассылает события → WebSocket frontend + Telegram-уведомления.
2. Команда пользователя → Application → Domain-проверка capabilities →
   `EspClient.set_relay()` → ожидание `ACK` → событие `device.state_changed`.
3. `AutomationEngine` (цикл каждые `AUTOMATION_INTERVAL_SEC`) и
   `ScenarioEngine` (каждый `SCENARIO_TICK_SEC`) работают поверх того же
   executor'а, что и ручные команды. Планировщик перебирает зарегистрированные
   аккаунты и выполняет цикл для каждого по отдельности.
