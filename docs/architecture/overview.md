# Архитектура системы

## Три уровня ответственности

```text
ESP8266        -> физическое исполнение (реле, датчик) и трансляция показаний
Backend        -> ВСЯ бизнес-логика: устройства, автоматизация, сценарии, понимание фраз
Frontend / TG  -> только интерфейс пользователя
```

* ESP8266 не принимает решений за систему: она знает только свои пины, сеть и адрес
  сервера.
* Frontend и Telegram не говорят с платой напрямую — только через бэкенд.
* Бэкенд — единственная точка, через которую проходят команды и автоматизация.
* Clean Architecture применяется **только к бэкенду**.

## Многопользовательская схема

Один бэкенд, один фронтенд, одна схема приложения — и персональная проекция этого
приложения для каждого аккаунта:

```text
                     ┌──────────────────────┐
                     │       Backend        │
                     │                      │
                     │ auth    аккаунт      │
                     │ devices живой дом     │
                     │ api     хранилище    │
                     └───────────┬──────────┘
                                 │
                  ┌──────────────┴──────────────┐
                  │                             │
             Аккаунт A                      Аккаунт B
                  │                             │
       ┌──────────┴──────────┐       ┌──────────┴──────────┐
       │                     │       │                     │
   устройства            плата   устройства            плата
   настройки          панель     настройки          панель
   автоматика        сценарии   автоматика        сценарии
```

Человек получает не копию приложения, а свою проекцию: хранятся данные и состояние,
а не отдельная сборка.

### Как обеспечивается изоляция

1. **Идентификатор.** Аккаунт получает `UserId` — UUID (`UserId.generate()`). Он
   связывает сущности между собой, но пропуском не является: вход идёт по токену.
2. **Владелец в таблице.** `devices`, `automation`, `scenarios`, `preferences`,
   `dashboard`, `esp_devices`, `esp_claims`, `board_networks` несут `user_id`, а
   дочерние строки (способности устройств, участники автоматизации, виджеты панели)
   каскадно снимаются вместе с родителем.
3. **Владелец в сигнатуре.** `DeviceRepository.list_all(user_id)`,
   `get(user_id, device_id)`, `delete(user_id, device_id)`: изоляция видна в коде,
   который делает запрос, а не спрятана в настройке транзакции.
4. **Аккаунт из токена.** `CurrentUserId` — зависимость FastAPI, достающая `UserId` из
   bearer-токена. Ни один маршрут не читает `user_id` из тела или из query.
5. **Изменчивое состояние по домам.** `HomeStateStore` держит в Redis по одному хешу на
   аккаунт (`redis_key_prefix` задаёт пространство имён), а переключает его атомарными
   Lua-скриптами: `HomeState` — состояние одного дома, и чужого дома в нём нет.
6. **События по аккаунтам.** `RedisEventBroker` публикует в канал одного аккаунта, а
   `WebSocketHub` отдаёт событие только сокетам его владельца. Общим каналом идёт
   единственное событие без хозяина — объявление не сопряжённой платы.
7. **Платы по аккаунтам.** `EspConnection` ведёт `BoardRegistry` с сессиями по
   `UserId`, а `BoardGateway.set_relay(user_id, board_id, ...)` адресует конкретную
   плату; ключ сопряжения уникален на всю систему.

Подстановка чужого UUID не даёт ничего: чужое устройство читается как отсутствующее
(`404`), а команда до его платы не доходит.

## Процессов два, и оба без состояния в памяти

```text
python -m backend.main           -> FastAPI + WebSocket интерфейса + сервер плат
                                    (жизненный цикл поднимает транспорт плат,
                                    концентратор событий, посев опорных фраз и бота)
python -m backend.worker_entry   -> ARQ-рабочий: цикл автоматики, такт сценариев,
                                    часовая чистка объявленных плат
        │                                │
        └────────────┬───────────────────┘
                     ▼
   Postgres (настроенные дома)   Redis (изменчивое состояние, события, аренды)
```

Фоновые циклы живут вне HTTP-процесса: перезапуск или вторая реплика веб-сервера не
умножают их. Рабочих может быть несколько одновременно, поэтому каждая задача по
аккаунту сначала берёт распределённую аренду (`RedisDistributedLock` с токеном и
продлением): из двух инстансов, взявших один период, ровно один его выполнит.
Аккаунты одного периода идут параллельно под семафором, каждый со своим таймаутом, так
что дом с недоступной платой не задерживает остальные.

Схема базы применяется ревизиями Alembic из `build/migrations` (`docker compose up`
запускает одноразовую службу `migrate`). Из кода таблицы не создаются никогда.

## Слои бэкенда

```text
Presentation   api/v1 (по маршруту на тему) + requests/responses, websockets (только
               эндпоинт), telegram (разговор бота), web, errors, messages,
               security_helpers, app_factory
     ↑
Composition    events/lifecycle — старт и остановка подсистем; main и worker_entry
     ↓
Application    use_cases (по одному сценарию в файле), services, dto (плоские, без
               логики), interfaces (repositories / queries / services / unit_of_work,
               сгруппированные по подпакетам), errors
     ↓
Domain         aggregates (только корни: User, Device, Scenario, EspDevice,
               DashboardState, AutomationSettings), entities (дочерние сущности и
               модели без подчинённых), value_objects (значения, перечисления и модели
               чтения), policies, exceptions, identifiers, events
     ↑
Infrastructure database (engine, unit_of_work, models, mappers, repositories, queries),
               brokers (Redis: состояние, события, аренды), esp (транспорт плат и
               кодек кадров), nlp (драйверы: pgvector, torch, HTTP модели), security,
               telegram (только транспорт бота), websockets (концентратор сокетов),
               workers (фоновые циклы), system (часы и журнал), di
```

Правила раскладки, которые держатся во всех слоях: модулей в корне пакета нет — то, что
раньше висело файлом (`clock.py`, `logging.py`, `unit_of_work.py`), либо собрано в
подпакет (`system`, `database`), либо остаётся одиночным модулем там, где он и должен быть.
Агрегат — только тот корень, без которого другие доменные объекты не существуют (или
чьи инварианты над ними держатся); всё остальное понижено до `domain/entities`, а
enum'ы живут отдельным файлом в `domain/value_objects`, а не попутчиком агрегата.
Порты прикладного слоя разложены по подпакетам (`boards`, `language`,
`messaging`, `security`, `state`, `system`), чтобы в одной папке не лежал список из
двадцати файлов.

Каждый внешний мир — отдельный адаптер в своём пакете: в `telegram` нет ни часов, ни
планировщика, ни состояния домов; фоновые циклы лежат в `workers`, а не прячутся за
транспортом бота.

Зависимости направлены внутрь. Домен не знает ни про FastAPI, ни про SQLAlchemy, ни про
Telegram, ни про конкретную библиотеку эмбеддингов — только про свои типы. Границы
проверяются тремя контрактами `import-linter` (`lint-imports`): слои по порядку, домен
свободен от фреймворков и внешних слоёв, прикладной слой не заглядывает в
инфраструктуру.

Граф зависимостей собирает Dishka (`infrastructure/di`), и провайдеры разложены по
областям видимости: `providers/app/<подсистема>.py` — одиночные адаптеры процесса
(`Scope.APP`, они сами запускаются и гасятся при закрытии контейнера),
`providers/use_cases/<фича>.py` — сборка сценариев (`Scope.REQUEST`, класс
`<Фича>UseCaseProvider`). Ключами контейнера остаются порты, а не их реализации, так что
заменить Redis или базу можно, не трогая сценарии. Домен через контейнер не
провайдерится: решатели вроде `DeviceSelector` ни от чего не зависят и строятся там, где
используются. Ни одного сервис-локатора: маршруты получают зависимости через
`FromDishka`, а не вынимают их из `app.state`. Целостность графа проверяется скриптом
`scripts/check_app_wires.py`, который запрашивает каждый узел — ленивый контейнер сам по
себе о недостающей зависимости не сообщает.

## Ключевые решения

| Решение | Обоснование |
| --- | --- |
| Логическое устройство ≠ реле | Соответствие «устройство — канал» хранит бэкенд, поэтому каналы переназначаются без перепрошивки |
| Способности (`ON/OFF/COOL/HEAT/HUMIDIFY/DEHUMIDIFY`) | Автоматизация ищет устройство по возможности, а не по имени и не по номеру реле |
| Аккаунт — первый аргумент сценария | Изоляция видна в сигнатуре, а не в договорённости |
| Коридор = цель + допуск | `target_temperature` и `temperature_tolerance` вместо `min/max`: границы не сойдутся в разных местах |
| Приоритеты `ControlSource`: аварийные > сценарий > автоматика > ручное | Детерминированное поведение при конфликте двух желаний |
| Окно ручного управления | Ручное действие ставит автоматику в сторону на `automation_manual_override_minutes`; записано реакцией, а не строкой в каждом сценарии |
| Изменчивое состояние в Redis | Дом переживает перезапуск процесса, а несколько инстансов видят одно и то же; окно переопределения и троттлинг сводок держатся нативными TTL |
| Ревизия строки (`version`) | Запись по устаревшему снимку не перетирает чужое изменение, а даёт отказ `409` |
| Токены без хранилища сессий (HS256 + claim `kind`) | Один секрет выдаёт и сессию интерфейса, и короткий ссылочный токен привязки Telegram; смена секрета разлогинивает всех |
| PBKDF2 с самоописывающейся формой | Префикс алгоритма оставляет переход на bcrypt правкой кода, а не переносом данных |
| Панель — данные, а не разметка | `widgets: [{type, device_id, title}]`; фронтенд остаётся универсальным рендерером |
| Плата дозванивается сама | Исходящее WebSocket-соединение по ключу сопряжения: стабильный IP плате не нужен |
| ArduinoJson на плате | Кадры читаются и пишутся документом на стеке: кавычка в имени сети больше не ломает кадр, а ручной strstr-разбор не нужен |
| Голосового пути нет | Распознавания речи в развёртывании нет, поэтому микрофон из протокола, прошивки и интерфейса убран |
| Опорные фразы в pgvector | Поиск ближайшего соседа оператором косинусного расстояния Postgres (индекс HNSW), а не список в памяти процесса |

## Конвейер понимания фраз

```text
нормализация → словарь (слова, обороты) → намерение
             ↘ не узнал → кодирование → ближайшая опорная фраза (pgvector) → намерение + уверенность
             → разбор параметров (числа, задержка, место, устройство) → команда приложения
```

Параметры предложения вычитываются из слов (`vocabulary` + `parser`). Намерение ищут в
два шага: сначала словарь (`lexicon`) узнаёт знакомые слова и обороты — это стоит
столько же, сколько сравнить строки, и работает на любом развёртывании; только
непонятое уходит в смысловой конвейер, который сравнивает векторы. Вектор нужен для
непривычной формулировки, но платить кодированием за каждую фразу незачем: у словаря
просят ответа на большинство запросов, а модель не держат в горячем пути.

Уверенность ниже `language_confidence_threshold` не исполняется: система задаёт
встречный вопрос. Если развёртывание настроило службу моделей
(`language_neural_commands`, `language_bootstrap_url`), смысловым конвейером становится
она, а местный остаётся запасным; недоступная модель не отключает дом — её отказ
записывается в журнал и цикл идёт местным путём. Кодировщика может не быть вовсе:
тогда словарь остаётся единственным конвейером, а предложение вне его словаря получает
ответ `503`, а не внутреннюю ошибку. Поэтому образ без `.[embeddings]` — полноценное
развёртывание для знакомых формулировок, а не сломанное.

## Потоки событий

1. Плата шлёт `STATE` / `SENSOR_DATA` → `HomeStateService` пишет положения каналов и
   показания в `HomeStateStore` → публикует `board.relay_changed`,
   `sensor.temperature_changed`, `sensor.humidity_changed` → WebSocket интерфейса и
   уведомления в Telegram.
2. Команда человека (REST, чат или бот) → `CommandDispatcher` выбирает сценарий по
   намерению → домен проверяет способность и канал → `DeviceControlService` приказывает
   плате и ждёт `ACK` → состояние пишется, затем публикуется `device.state_changed`.
   Порядок постоянен: транзакция закрыта до обращения к железу, событие отправлено после
   коммита, поэтому отклонённая команда не оставляет ни записи, ни события.
3. `AutomationService` (каждые `automation_cycle_sec`) и `ScenarioAdvancer` (каждый
   `automation_scenario_tick_sec`) идут через того же исполнителя, что и ручные команды:
   одно правило переключения не продублировано в трёх местах. Планировщик перебирает
   зарегистрированные аккаунты и выполняет цикл для каждого отдельно.
